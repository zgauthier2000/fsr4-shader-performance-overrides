## What's new

- **Lossy DLL in Ultra Performance (Ultra Performance only, not representative of other modes):** it now skips frames there
  too. 4K: 3.18 to 2.50 ms per frame; Shadow of the Tomb Raider at 4K Ultra Performance: 9% more frames. The price: in that mode
  its picture is further from AMD's than before (areas just uncovered by moving objects, sky seen through leaves, tiny sparks,
  thin wires in a fast pan).
- **Lossy DLL in every other mode:** the same picture and speed as `dll-2026-10-14`.
- **Exact DLL:** the same picture as AMD's, and about 0.02 ms per frame faster than `dll-2026-10-14`'s exact DLL at 4K: 3.16 ms
  against 3.18 (AMD's shaders 5.00 ms; Windows timing kit, Balanced size, RX 7800 XT). In the game benchmark, 0.2% more frames than
  with `dll-2026-10-14`'s exact DLL.
- **RX 6000 cards, the RX 7600 and integrated graphics:** both DLLs changed their last shader in ways that may help or cost on
  these chips, and neither is measured there yet. [The timing kit](../../timing-kit/README.md) measures it.

What this release changes, in figures and pictures, against the release before it. Both DLLs change: the exact DLL is a little
faster with the same picture, and the lossy DLL now also skips frames in Ultra Performance.

## Change 1: frame skip in Ultra Performance (Ultra Performance only)

> [!IMPORTANT]
> Everything in this section is **Ultra Performance only and not representative of the lossy DLL in other modes.**

Up to `dll-2026-10-14` the lossy DLL ran the network on every frame in Ultra Performance (a render size under half the output size): in
that mode it was about as fast as the exact DLL. Now it skips frames there too. Frames that run the network all have the same sign of
camera jitter, so in Ultra Performance, where one render pixel covers three output pixels, they only ever sample one half of each render
pixel; thin lines in the other half were missing from the picture and shimmered. So one in three of the frames that would be skipped runs
the network all the same (those whose vertical jitter is in the lowest sixth), which brings the other half into view now and then. About
one frame in three is skipped, instead of every other one.

| Ultra Performance only: time per frame, ms (Windows timing kit under Proton, moving, mean of 6 rounds) | AMD's shaders | Exact DLL | `dll-2026-10-14` lossy | This release's lossy |
|---|---|---|---|---|
| 1080p output (render 640 x 360) | 0.94 | 0.89 | 0.92 | **0.76** |
| 1440p output (render 853 x 480) | 2.10 | 1.42 | 1.46 | **1.17** |
| 4K output (render 1280 x 720) | 4.64 | 3.07 | 3.18 | **2.50** |

The kit uses the 72 jitter steps FSR asks a game for in Ultra Performance.

## Change 2: the skipped-frame guard rests where nothing moves

A skipped frame takes the new frame alone where the old picture is far darker in every color channel (a guard against dark bands when
something scrolls in from outside the screen). In Ultra Performance a thin wire is often missing from the old picture, because the frames
that run the network sample beside it; a skipped frame whose samples hit it then tripped the guard, and the wire flashed. Where the
picture does not move nothing scrolls in, so the guard now stays out there.

| Thin wires and fireflies at rest, Ultra Performance only (auto exposure off) | AMD's shaders | Frame skip in Ultra Performance with the old guard | This release |
|---|---|---|---|
| Thin wire at rest: change per frame | 1.13 | 8.70 | 1.38 |
| Fireflies: flicker counts | 4, 0 | 264, 157 | 9, 4 |

(The middle column is an Ultra Performance test build; no release skipped frames there.) In Balanced and the other modes this changes
almost nothing: see below.

## Change 3: fewer registers in the lossy DLL's last shader

The same picture as `dll-2026-10-14` (every check identical). The last shader works out the range of its nine color samples as it reads
them, and reads the old picture's 3 x 3 pixels in three rows; frames that run the network keep their own copy of that code. On graphics
chips with the smaller register file (RX 6000 cards, the RX 7600, integrated graphics such as the Steam Deck's) it needs 80 registers
instead of 128, so 12 groups of threads run at once instead of 8 (compiler figures; RX 7800 XT unchanged at 96 and 16). On the
RX 7800 XT it costs at most 0.01 ms per frame at 4K (kit: 2.228 against 2.231 ms, Balanced size).

## Change 4: shared color taps in the exact DLL's last shader

Each thread of the last shader writes 2 x 2 output pixels, and each of those reads and converts the 3 x 3 colors around it. Those
four windows lie in one 4 x 4 window, so the shader now reads and converts each of those 16 colors once instead of up to four times. Same
picture as AMD's, byte for byte (72 test-rig cases from native to 5K, and 30 in Ultra Performance, both DLL flavors and the Linux files).

| Exact DLL, RX 7800 XT | `dll-2026-10-14` | This release |
|---|---|---|
| Last shader alone, 4K (Linux timing kit, both orders) | 0.647 ms | 0.609 ms (−5.9%) |
| Whole upscaler, 4K Balanced size (Windows kit, 6 rounds) | 3.180 ms | 3.155 ms |
| Shadow of the Tomb Raider, 4K Balanced: frames rendered | 16,924 | 16,963 / 16,967 |

It needs more registers: 120 instead of 96 on the RX 7800 XT (12 groups of threads instead of 16), and on RX 6000 cards, the RX 7600 and
integrated graphics 8 instead of 16. **Measured since (Windows timing kit, against the previous form in the same run):** it is not
slower there but about 1% faster (RX 6000 cards 0.6 to 0.8%, 14 reports; RX 7600 1.4 to 1.5%, 3 reports; a Radeon 890M 1.9 to 3.6%,
one report; RX 7800 XT and RX 7900 1.2 to 1.4%), with the same picture.

## Balanced and the other modes: almost nothing changes

The lossy DLL at the Balanced preset's size (the full quality check of every release, auto exposure off and on): every moving-scene row
is identical to `dll-2026-10-14`'s. At rest the guard of change 2 moves a few rows by a hair: film grain up to 2% steadier, firefly
flicker counts 13, 1 to 15, 1 with auto exposure off (AMD's 4, 0), tiny fast sparks shown 73.6 to 73.5%. Its speed is the same.

## What got worse

- **Ultra Performance only:** the lossy DLL's picture is further from AMD's than `dll-2026-10-14`'s was in that mode (see the table in
  change 1): areas just uncovered by a moving object, isolated bright dots, tiny fast sparks, thin wires in a fast pan, and with auto
  exposure on the old image beside an object moving against the camera's pan. `dll-2026-10-14` did not skip frames there, so it was as
  slow as the exact DLL.

## Checks

- **DLL = Linux files:** the lossy DLLs give the Linux files' frames, byte for byte: 48 of 48 test-rig comparisons at the Balanced size and
  20 of 20 in Ultra Performance (1080p, 1440p, 4K and 5K moving, 4K still; auto exposure off and on).
- **Exact = AMD:** the exact DLLs and Linux files, 72 of 72 cases and 30 of 30 in Ultra Performance.
- **The tools rebuild it:** the repository's tools with their defaults rebuild these DLLs and Linux files byte for byte; with the new
  options switched off they rebuild `dll-2026-10-14`'s.
- **Not checked:** Windows itself (the DLLs ran under Proton), the smaller graphics chips, and Ultra Performance in a game scene picked
  for uncovered areas or thin wires.
